# Chase architecture

## Scope and runtime

Chase v0.1 is a guest-first iOS/Android frontend prototype. It uses the official Expo SDK 57 template, React Native, strict TypeScript, and Expo Router. Web provides an additional preview path. Native directories are generated by Expo when needed; they are not maintained by hand.

Catalog lookup and available ungraded quotes use the public TCGdex API without credentials. Optional email/password authentication uses Supabase's public URL and publishable key. The development CardSight camera path uses a separate local proxy with a server-only vendor key. A hosted Supabase scanner backend is implemented for controlled beta deployment; see HOSTED_SCANNER.md. Verified store purchases, historical market data and cloud collection synchronization remain unfinished integrations with explicit UI states.

## Domain and service boundaries

The domain types include `Card`, `CardVariant`, `MarketPrice`, `Collection`, `CollectionItem`, `UserProfile`, `SubscriptionEntitlement`, and `ScannerTrialState`. `Card.id` describes a collectible printing/finish, not just a Pokémon. TCGdex's canonical card ID lives separately in `Card.catalogIdentity.id`; `tcgdex:<language>:<canonical-id>:<variant-key>` is the collectible key used by Collection and Organize. Normal, Holo, Reverse holo and other supported variants cannot share ownership or pricing accidentally.

Service contracts isolate the UI from providers:

- `CardCatalogService`: compatibility contract for listing, looking up, and searching catalog entries; the TCGdex adapter additionally exposes incremental queries, expansion lists/details and variant resolution.
- `CardRecognitionService`: return a recognized sample without owning quota mutation.
- `MarketPricingService`: provide a typed estimate and source.
- `CollectionRepository`: persistence boundary for future collection adapters.
- `SubscriptionService`: entitlement boundary for future verified subscriptions.
- `AccountAuthenticationService`: email/password accounts, server-verified identity and email callbacks, independent of local collection ownership.

The runtime catalog calls TCGdex through a modular adapter with request deduplication and cached results. It resolves official `/sets`, `/sets/{id}`, `/cards` and `/cards/{id}` resources. English is the initial configured language; language is part of provider identity so later Japanese/other catalogs need not change ownership keys. Screens use normalized cards rather than parsing provider payloads. See [TCGDEX_INTEGRATION.md](TCGDEX_INTEGRATION.md) for pricing safeguards, cache behavior and device checks.

Retained mocks provide deterministic frame/recognition demonstrations and legacy editorial examples, with copied results to avoid mutating shared sample data. The mock repository is in memory; the application separately persists its prototype state in AsyncStorage. A network failure never replaces real catalog results with a mock catalog. Future SQLite/cloud adapters can replace persistence without placing provider calls inside screen components.

Supabase authentication is a separate adapter; CardSight recognition uses the documented development proxy. Cloud collection synchronization, a deployed authenticated recognition backend and RevenueCat-backed native purchases remain later work. Never place private credentials in the mobile client.

## State and persistence

`ChaseProvider` exposes a typed context with prototype state, derived collection totals, centralized entitlements, and local actions. It loads AsyncStorage key `chase.prototype.v1` before the normal app flow. Stored JSON is normalized so invalid cards, quantities, dates, and trial values cannot reach the inventory UI.

The persisted state includes onboarding completion, current mock plan, successful complimentary recognition count, and collection items with quantities and addition dates. New real catalog items additionally retain a validated `Card` snapshot, so ownership/detail references survive a restart or provider outage. Pending ScanSession items use the same optional snapshot strategy in their separate store. Registry hydration validates the full provider/variant identity; malformed remote snapshots expose recovery rather than silently deleting owned cards. Existing legacy rows remain valid without a snapshot or ID migration.

Writes are queued to preserve order. Loading failures expose a retry; persistence failures explain that current changes may only last for the session. Do not replace unread saved data silently. Provider cache refreshes can update displayed reference data but must not reinterpret saved ownership IDs.

AsyncStorage is device-local storage, not a database sync engine or secure credential store. A future database migration should introduce versioned storage and repository-backed collection access before adding cloud synchronization.

## Centralized entitlements

Domain rules derive entitlements through `getEntitlements`; screens consume the shared result. Free permits 50 **total copies**, one collection, catalog browsing, manual search, available ungraded prices, and one complimentary successful recognition. Pro represents unlimited copies/scans and future multiple collections, graded prices, and CSV export.

Recognition eligibility is checked before the mock service runs and again after it returns. A valid identification is first durably staged in ScanSession; only then is the Free trial recorded. A session marker repairs an interrupted trial write after restart. Opening the scanner, cancellation before staging, and recognition/storage errors do not consume it. A recognition lock prevents concurrent requests. Saving to permanent Collection is a separate explicit action from Organize.

Quantity mutations validate positive safe integers and the aggregate Free limit. Existing entries gain another copy; separate variants use separate IDs. Valuation sums available quotes for every saved copy, converts source currencies using the disclosed fixed sample rate and accumulates in cents to avoid visible floating-point artifacts. Unpriced copies remain owned and are counted separately; their missing values are not fabricated. Market values are estimates rather than guaranteed resale amounts.

`setDevPro` is guarded by `__DEV__`; its Profile switch is labeled **Development only · simulate Pro**. This local flag is not purchase verification. Paid recognition and subscription permissions must eventually be enforced by a secure backend with verified store state. The entitlement flags for graded prices, CSV, and multiple collections express future capability, not completed features.

Production hydration always restores Free access, preserving owned copies. A development downgrade also preserves ownership above 50 copies and permits reductions; new copies are blocked until the Free allowance is available. Scanner unmount aborts its result handling, and canceled recognition never consumes the trial.

## Account and external links

`AuthProvider` wraps the existing providers without gating guest navigation. `AccountService` implements Supabase email/password registration, sign-in, password recovery/update and local-session logout. Startup and auth changes verify identity through `auth.getUser()`; cached user metadata alone does not establish an authenticated identity. Profile uses that separate verified profile. Authentication never mutates Collection, pending ScanSession, currency, trial accounting or subscription access.

Native refresh tokens and PKCE verifiers live in a serialized, chunked SecureStore adapter; browser sessions use localStorage for same-browser PKCE links. Session manifests commit only after all encrypted chunks are written. Account HTTP requests bound both headers and response bodies; errors expose whitelisted messages. Expo Crypto supplies native secure randomness and SHA-256 for PKCE, not a general WebCrypto implementation. The app does not use local `getClaims()` verification. Email callbacks accept the code and SDK flow ID, exchange once and route recovery to password update. See [SUPABASE_INTEGRATION.md](SUPABASE_INTEGRATION.md) for configuration and device checks.

Restore Purchases explains that no store restoration occurs. Account deletion remains explicitly unfinished and never claims success. Future cloud sync must define explicit guest import, user isolation and RLS before uploading device-local ownership; logging out currently preserves the same local collection and pending scans. A future deletion flow must explain consequences and require explicit confirmation.

Privacy, Terms, and Support start with `null` URLs in `src/config/links.ts`. Configure reviewed HTTPS destinations before release. Their screens explain missing configuration and show a working browser action only when a valid HTTPS destination exists.

## Validation and remaining integration work

Use `npm run typecheck`, `npm run lint`, `npm run test`, and `npm run export:mobile`. Domain/service tests cover the important trial, quantity, limit, identity, and valuation rules; mobile exports validate JavaScript bundling for iOS and Android. These checks do not establish native device behavior, real camera recognition, secure backend enforcement, or signed store readiness.

Validate navigation, safe areas, large text, state restoration, errors, public API connectivity and Free/Pro boundaries on iOS and Android devices before release. Linux cannot run an iOS simulator, and this environment does not supply an Android emulator or `adb`. Future production work should be incremental: a real camera/frame and recognition adapter, versioned database persistence, authenticated cloud sync, verified subscriptions, live FX if required, and reviewed legal/support destinations.

## Printing presentation and legacy keys

`src/data/cardVisuals.ts` maps legacy keys to local full-print images, landscape moods and image limitations, and resolves remote card artwork without borrowing a legacy illustration. `CardPrint` displays the shared printing image with a safe unavailable state. Active screens use purpose-specific compositions; the previous collector landscapes are no longer used. The retained editorial/sample catalog has 17 entries and 16 images (Pikachu variants share a disclosed printing reference). New catalog browsing loads TCGdex artwork and provider quotes independently of these examples.

The original mock incorrectly identified Eevee as Base Set 2 68/130 and Mew as SWSH053. Display metadata now matches the actual supplied prints: Eevee 51/130 and Wizards promo Mew 9. The internal `base2-68` and `swshp-053` keys deliberately remain stable, preserving existing AsyncStorage ownership and quantities. They are reserved legacy application keys, not external provider IDs. A new real card with a similar canonical ID uses the namespaced collectible identity; it cannot overwrite or silently merge with a saved legacy entry. No automatic remapping is attempted.

## Simulated price tracking

`src/services/priceHistory.ts` is a pure deterministic adapter for daily USD sample series. It exposes 7D, 1M, 3M and 1Y windows anchored to the catalog date, October 1, 2026. All windows are trailing slices of the same per-printing curve; exact endpoints equal current mock prices. Portfolio aggregation and holding movement calculations multiply every valid copy in cents. The module has no network calls, state mutation or provider UI dependency.

The curve revalues current legacy sample holdings at sample historical prices. It deliberately ignores `addedAt` and does not infer transactions, cost basis, profit or past ownership. Real provider cards have no generated history, and a mixed/real portfolio does not display a sample combined curve or fictitious movement. An empty collection stays zero. The wallet's sample collection is presentation state only and never enters the provider or AsyncStorage.

`PriceChart` renders native line segments and supports pointer selection, native accessibility adjustment, web keyboard controls and exact date/value disclosure. A keyed chart resets inspection when its date window or endpoint changes. `RangeSelector` is a reusable control, while onboarding, wallet and card detail retain distinct layouts. No chart dependency or native package was added.

Search defaults to the full newest-first set directory; `view=cards` opens global card search, and `setId` opens an expansion. Home lists the same API-provided sets using logos. The set directory requests `sort:field=releaseDate&sort:order=DESC` before the provider projects its briefs (which omit dates). Set browsing hydrates all matching printing prices in batches of at most six, chooses each printing’s most valuable supported finish with its own quote, and sorts before pagination. Complete-set price snapshots share the bounded persistent cache, preserve the oldest source-cache timestamp, and keep the set index available after per-card eviction. Missing quotes sort last, with natural collector-number ties; its count is the actual filtered index length, not a fetched global page size. Global card search starts on input and clearly distinguishes loaded results from a known total. Search accepts an initial query or expansion filter; provider requests remain behind the catalog service. Original catalog IDs, copy validation and Free downgrade rules are preserved. The continuous-scanner implementation adds optional save receipts to collection persistence and a separate pending-session key; see [SCANNER_WORKFLOW.md](SCANNER_WORKFLOW.md).

## Home artwork rotation

`src/services/featuredCards.ts` owns the explicit three-printing editorial pool and draws randomly without replacement. Remaining IDs and the last shown card are saved separately under `chase.home-artwork.v1`. Corrupt rotation data resets safely. A new cycle excludes the previous cycle’s last card from its first draw. Catalog expansion does not automatically expand this pool.

`src/features/home/featuredCardSession.ts` caches one selection promise for the JS app lifetime, so duplicate effects, route remounts and tabs cannot advance the rotation. `ChaseProvider` loads the selection alongside collection hydration before showing navigation. A full app restart/reload draws again; foregrounding an already-running session keeps its card. Rotation storage failure falls back to session-only artwork without blocking the collection; cross-launch non-repetition requires working device storage. The collection schema, quantities, entitlements and scan accounting are untouched.

## Onboarding price carousel

`src/features/onboarding/PriceCarousel.tsx` uses an explicit five-card legacy editorial selection, separate from Home's three-card launch pool. A native horizontal `Animated.ScrollView` snaps to a fixed card interval, with scroll-driven transforms and the nearest centered index controlling its sample quote. These onboarding examples are not live catalog requests. The first screen's body permits edge previews; later onboarding screens retain their existing layouts. Chevrons, native accessibility increment/decrement and web keyboard arrows/Home/End provide non-swipe controls. There is no autoplay, provider mutation, scan use or saved selection.

Profile uses the catalog entry `swsh8-269` (Mew VMAX, Fusion Strike 269/264) in the shared CardPrint component. Its removed membership summary affects presentation only. Explore Chase Pro and Restore Purchases are grouped below settings; existing routes, entitlement enforcement, guest behavior and development simulation remain unchanged. This card is not added to Home’s explicitly restricted artwork pool.

## Display currency

`CurrencyProvider` persists the independent display preference under `chase.currency.v1` and owns one shared modal opened by Collection and Profile. Only USD and EUR are accepted; missing or invalid settings default to USD. A selection is applied after storage succeeds; failures keep the previous currency and the dialog open for retry. Collection ownership, onboarding, plan and scanner state are stored separately and are not rewritten by currency selection.

Market quotes retain their native USD or EUR amount and source. Legacy sample history remains USD; portfolio valuation normalizes available quotes for aggregation. `src/services/currency.ts` performs conversion and rounding; `useCurrency().formatMoney(amount, sourceCurrency)` formats price surfaces, chart inspection and accessible monetary labels in the saved display currency. This avoids compounding conversion after repeated switches. Conversion currently uses the fixed **sample** rate 1 USD = 0.92 EUR in either direction, shown in the selector. It is not a live FX feed. Changing display currency does not change printing identity, quote source or finish. A future rate provider can replace this service without changing the inventory schema.

The Collection shortcut retains the original badge's dimensions and placement. Its blue appearance signals interaction; the overlay extends the touch area without moving surrounding content. Profile opens the same modal and displays the current choice. The legacy account currency route also provides access to that modal.

The third onboarding illustration uses a local illustrative portfolio series from September 1 to October 1, 2026: 1,120 to 1,280 sample USD (+14.29%). It is independent of catalog prices and user holdings. The net-positive curve contains small fluctuations; Rayquaza VMAX is editorial artwork, not an implied source of that balance. The two-printing footer was removed. Display currency still uses the shared formatter. This illustration does not supply a historical feed for real Collection or card records.

## Development recognition boundary

`LiveScannerScreen` and `LiveScannerCamera` provide bounded oriented captures, guide-aligned crop/resize, local `liveCardFrames` heuristic analysis and perceptual presentation tokens. Camera pixels/base64 remain ephemeral and never enter the persisted session. The existing controller still gates stability, cooldown, one recognition and cancellation. `CardSightRecognitionService` consumes a Chase-owned sanitized proxy protocol, then `resolveCardSightCandidates` validates exact English TCGdex identity and finish metadata. Finish review rows withhold pricing and portfolio totals until explicit confirmation; Collection persistence and operation receipts are unchanged.

`server/cardsightProxy.ts` is not imported by the app. Its development HTTP adapter isolates the vendor secret, limits bodies/concurrency/rate/run usage and provides digest-based request receipts. The default runner injects `server/cardsightTransport.ts`: binary JPEG to the documented CardSight `POST /v1/identify/card`, server-only `X-API-Key`, fixed HTTPS origin, bounded JSON reads and no automatic retries. Physical detections are distinct from alternative printing suggestions. High/Medium/Low remain evidence tiers; unknown language requires English printing confirmation, and missing/ambiguous parallel evidence stays unpriced until Organize finish review. Health reports local adapter/key configuration, not authenticated provider readiness. Schema-based fixtures validate the adapter through client/catalog/session/save boundaries; actual vendor and phone validation remain pending. Production needs a deployed authenticated backend, durable quotas and privacy review. See `CARDSIGHT_SCANNING.md`.

After Android feedback, recoverable errors rearm on a new physical presentation and capture state is scoped to each measured native preview instance. The camera has a capture deadline and bounded reopen; navigation never clears accepted locks or staging. A sole supported catalog finish can be inferred when no conflicting provider evidence exists.

`CatalogResolutionError` retains whitelisted candidates and matching diagnostics. Optional `ScanSession.unresolved` stores these separately from canonical rows and Collection. Retry matching reuses metadata without another provider call; the dedicated `/match-scan/[id]` route lets users explicitly choose a printing. `RecognitionLinks` caches user-confirmed cross-provider IDs for future lookups without changing previous ownership. Pending matches have no quote and cannot be saved as ownership. Existing v1 sessions, snapshots, operation receipts and Free limits remain compatible. See the Android checklist and limitations in `CARDSIGHT_SCANNING.md`.


The p15 continuity follow-up adds `LiveScannerPipeline`: local thumbnails continue during provider/catalog work, while only eligible stable presentations encode/upload a full JPEG. Capture-start timing prevents slow native processing from looking like a camera gap. Artwork-region comparisons distinguish similar commons, and identity verification is separated from permission to count a physical copy. Optional catalog I/O has bounded deadlines; durable ScanSession persistence remains authoritative. Development-only scalar diagnostics expose the stage and rejection reason without retaining photos or credentials. See [the reproduction report](SCANNER_CONTINUITY_DIAGNOSIS.md).

## Hosted recognition boundary

`supabase/functions/cardsight-scanner` reuses the same pure protocol and vendor adapter as the Node proxy. The app selects it only with `EXPO_PUBLIC_SCANNER_BACKEND=supabase`; otherwise the existing development configuration remains in effect. Current Supabase JWTs are obtained per request. The handler verifies the caller against Auth, automatically provisions Free for verified anonymous/registered identities and uses atomic PostgreSQL claims/lease-bound settlements for usage and replay across replicas. No vendor or admin credential is bundled in the app. The migration enables RLS and revokes all scanner-table/RPC access from app roles.

Automatic Free access permits one positive provider recognition and separately caps attempts; empty detections/provider failures do not consume the success allowance. Existing optional beta overrides survive. The local trial is still recorded only after staging, independently of this provider quota; failed canonical matches can be retried in Organize without another upload. The development plan flag cannot authorize server Pro. Registration links an anonymous UUID in place so it cannot refill its quota. The workflow applies additive migrations and enables anonymous sign-ins using the server-only administrative token; deployment and the vendor secret remain operational steps. Verified RevenueCat-backed Pro is pending. Photos remain transient; private receipts retain only whitelisted metadata. Collection and pending-session schemas are unchanged. See [HOSTED_SCANNER.md](HOSTED_SCANNER.md) for activation, limits, retention and verification.

Guest scanning uses `createScannerSession` only when the real scanner is opened. It deduplicates overlapping anonymous sign-ins and reuses persistent Auth storage. `AuthProvider.scannerIdentity` tracks the verified technical identity independently of the visible profile; anonymous users remain Guest collector. Account creation upgrades the guest through Auth updateUser rather than creating a fresh UUID. No local collection/session ownership is uploaded or reassigned.
