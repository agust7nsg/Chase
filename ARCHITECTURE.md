# Chase architecture

## Scope and runtime

Chase v0.1 is a guest-first iOS/Android frontend prototype. It uses the official Expo SDK 57 template, React Native, strict TypeScript, and Expo Router. Web provides an additional preview path. Native directories are generated by Expo when needed; they are not maintained by hand.

The initial runtime needs no API credentials. Authentication, store purchases, camera capture, external recognition, live pricing, and cloud synchronization are deliberately unfinished integrations with explicit UI states.

Route files delegate to feature screens. Keep application logic and non-route helpers outside `src/app`. The root stack contains onboarding, tabs, scanner, paywall, inventory, catalog/detail, and account screens; the tabs are Home, Collection, and Profile.

## Domain and service boundaries

The domain types include `Card`, `CardVariant`, `MarketPrice`, `Collection`, `CollectionItem`, `UserProfile`, `SubscriptionEntitlement`, and `ScannerTrialState`. A card ID describes a particular printing and variant, not just a Pokémon. Distinct printings and variants remain distinct inventory entries.

Service contracts isolate the UI from providers:

- `CardCatalogService`: list, look up, and search catalog entries.
- `CardRecognitionService`: return a recognized sample without owning quota mutation.
- `MarketPricingService`: provide a typed estimate and source.
- `CollectionRepository`: persistence boundary for future collection adapters.
- `SubscriptionService`: entitlement boundary for future verified subscriptions.

Mocks provide deterministic local behavior and copied results to avoid mutating shared sample data. The mock repository is in memory; the application separately persists its prototype state in AsyncStorage. Future SQLite/cloud adapters can replace these boundaries without placing provider calls inside screen components.

Potential later services include TCGdex, a commercial recognition API, Supabase, RevenueCat, and SQLite. Select and connect them in later tasks. Never place private credentials in the mobile client.

## State and persistence

`ChaseProvider` exposes a typed context with prototype state, derived collection totals, centralized entitlements, and local actions. It loads AsyncStorage key `chase.prototype.v1` before the normal app flow. Stored JSON is normalized so invalid cards, quantities, dates, and trial values cannot reach the inventory UI.

The persisted state includes onboarding completion, current mock plan, successful complimentary recognition count, and collection items with quantities and addition dates. Writes are queued to preserve order. Loading failures expose a retry; persistence failures explain that current changes may only last for the session. Do not replace unread saved data silently.

AsyncStorage is device-local storage, not a database sync engine or secure credential store. A future database migration should introduce versioned storage and repository-backed collection access before adding cloud synchronization.

## Centralized entitlements

Domain rules derive entitlements through `getEntitlements`; screens consume the shared result. Free permits 50 **total copies**, one collection, catalog browsing, manual search, basic sample prices, and one complimentary successful recognition. Pro represents unlimited copies/scans and future multiple collections, graded prices, and CSV export.

Recognition eligibility is checked before the mock service runs. The complimentary trial is recorded only after a valid sample result. Opening the scanner, canceling, or an error does not consume it. A recognition lock prevents concurrent recognition requests. Adding a recognized card is a separate user-confirmed action.

Quantity mutations validate positive safe integers and the aggregate Free limit. Existing entries gain another copy; separate variants use separate IDs. Valuation sums every saved copy and accumulates prices in cents to avoid visible floating-point artifacts. Market values are estimates rather than guaranteed resale amounts.

`setDevPro` is guarded by `__DEV__`; its Profile switch is labeled **Development only · simulate Pro**. This local flag is not purchase verification. Paid recognition and subscription permissions must eventually be enforced by a secure backend with verified store state. The entitlement flags for graded prices, CSV, and multiple collections express future capability, not completed features.

Production hydration always restores Free access, preserving owned copies. A development downgrade also preserves ownership above 50 copies and permits reductions; new copies are blocked until the Free allowance is available. Scanner unmount aborts its result handling, and canceled recognition never consumes the trial.

## Account and external links

The app does not create a fake signed-in state. Profile offers Create Account and Sign In entry points that explain their unfinished integration. Restore Purchases explains that no store restoration occurs. Logout and deletion workflows are reserved for real authenticated accounts; the prototype explains their prerequisite and does not claim success. A future deletion flow must explain consequences and require explicit confirmation.

Privacy, Terms, and Support start with `null` URLs in `src/config/links.ts`. Configure reviewed HTTPS destinations before release. Their screens explain missing configuration and show a working browser action only when a valid HTTPS destination exists.

## Validation and remaining integration work

Use `npm run typecheck`, `npm run lint`, `npm run test`, and `npm run export:mobile`. Domain/service tests cover the important trial, quantity, limit, identity, and valuation rules; mobile exports validate JavaScript bundling for iOS and Android. These checks do not establish native device behavior, real camera recognition, secure backend enforcement, or signed store readiness.

Validate navigation, safe areas, large text, state restoration, errors, and Free/Pro boundaries on iOS and Android devices before release. Linux cannot run an iOS simulator, and this environment does not supply an Android emulator or `adb`. The future production work should be incremental: real card assets/catalog, camera and recognition adapter, versioned database persistence, authenticated cloud sync, verified subscriptions, and reviewed legal/support destinations.

## Printing presentation and legacy keys

`src/data/cardVisuals.ts` maps stable catalog keys to local full-print images, landscape moods and image limitations. `CardPrint` displays the shared printing image. Active screens use purpose-specific compositions; the previous collector landscapes are no longer used. The expanded catalog has 16 entries and 15 images (Pikachu variants share a disclosed printing reference). All values still use the mock pricing contract.

The original mock incorrectly identified Eevee as Base Set 2 68/130 and Mew as SWSH053. Display metadata now matches the actual supplied prints: Eevee 51/130 and Wizards promo Mew 9. The internal `base2-68` and `swshp-053` keys deliberately remain stable, preserving existing AsyncStorage ownership and quantities. They are legacy application keys, not external provider IDs; any future live adapter must map them explicitly to the verified printing. Domain rules and the persistence schema are unchanged.

## Simulated price tracking

`src/services/priceHistory.ts` is a pure deterministic adapter for daily USD sample series. It exposes 7D, 1M, 3M and 1Y windows anchored to the catalog date, October 1, 2026. All windows are trailing slices of the same per-printing curve; exact endpoints equal current mock prices. Portfolio aggregation and holding movement calculations multiply every valid copy in cents. The module has no network calls, state mutation or provider UI dependency.

The curve revalues current holdings at sample historical prices. It deliberately ignores `addedAt` and does not infer transactions, cost basis, profit or past ownership. An empty collection stays zero. The wallet's sample collection is presentation state only and never enters the provider or AsyncStorage.

`PriceChart` renders native line segments and supports pointer selection, native accessibility adjustment, web keyboard controls and exact date/value disclosure. A keyed chart resets inspection when its date window or endpoint changes. `RangeSelector` is a reusable control, while onboarding, wallet and card detail retain distinct layouts. No chart dependency or native package was added.

`/search?query=...` initializes the existing catalog filter for Home's set shortcuts. The persistent state shape, original IDs, quota handling, recognition cancellation, serialized writes and Free downgrade rules are unchanged.

## Home artwork rotation

`src/services/featuredCards.ts` owns the explicit three-printing editorial pool and draws randomly without replacement. Remaining IDs and the last shown card are saved separately under `chase.home-artwork.v1`. Corrupt rotation data resets safely. A new cycle excludes the previous cycle’s last card from its first draw. Catalog expansion does not automatically expand this pool.

`src/features/home/featuredCardSession.ts` caches one selection promise for the JS app lifetime, so duplicate effects, route remounts and tabs cannot advance the rotation. `ChaseProvider` loads the selection alongside collection hydration before showing navigation. A full app restart/reload draws again; foregrounding an already-running session keeps its card. Rotation storage failure falls back to session-only artwork without blocking the collection; cross-launch non-repetition requires working device storage. The collection schema, quantities, entitlements and scan accounting are untouched.

## Onboarding price carousel

`src/features/onboarding/PriceCarousel.tsx` uses an explicit five-card editorial selection, separate from Home's three-card launch pool. A native horizontal `Animated.ScrollView` snaps to a fixed card interval, with scroll-driven transforms and the nearest centered index controlling the quote. Card prices come from the existing catalog. The first screen's body permits edge previews; later onboarding screens retain their existing layouts. Chevrons, native accessibility increment/decrement and web keyboard arrows/Home/End provide non-swipe controls. There is no autoplay, provider mutation, scan use or saved selection.
